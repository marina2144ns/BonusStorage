## Назначение проекта

`BonusStorage` — внутреннее Java-приложение для хранения истории бонусных операций по документам розничной системы.

Общий поток данных:

1. SQL Server Agent запускает `dbo.UploadBonusDocuments`.
2. Процедура читает изменившиеся документы напрямую из SQL-базы 1С.
3. Документы сохраняются в `BonusStorage.dbo.Documents`.
4. Java-приложение выбирает документы с `IsChanged = 1`.
5. Приложение вызывает HTTP-сервис «Бонусник».
6. Полученные события сохраняются в `dbo.BonusesInDocuments`.

В проект также добавлена витрина:

- `dbo.InformationCards`;
- `dbo.PersonPhones`.

Для неё подготовлены DDL и две процедуры инкрементальной загрузки из базы 1С.

Проверь самостоятельно и подтверди кодом, а не предположениями:

   - недоступности «Бонусника»;
   - HTTP-коде, отличном от 200;

   - неполном ответе;
   - ошибке при сохранении части бонусных событий.
3. Действительно ли работает `@Transactional`.
4. Действительно ли работает `@Scheduled`.
5. Может ли текущий проект собраться с зависимостями из `pom.xml`.
6. Есть ли рабочие секреты в отслеживаемых Git-файлах и истории.
7. Соответствуют ли JPA-сущности текущему DDL.
8. Корректно ли процедуры используют `CurrentVersion`.
9. Что происходит при удалении последнего телефона физлица.
10. Что произойдёт при параллельном запуске процедур.
11. Есть ли ошибки в цикле старой `UploadBonusDocuments`.
12. Насколько безопасна первоначальная загрузка нескольких миллионов строк.

## Принципы дальнейшей разработки

Следуй этим правилам во всех последующих заданиях.

### Работа по одной задаче

- Не смешивай независимые исправления.
- Не расширяй область задачи без согласования.
- Не выполняй попутный косметический рефакторинг.
- Не меняй бизнес-семантику молча.
- Если обнаружена соседняя проблема, опиши её отдельно.

### Только необходимые изменения

Не предлагай и не внедряй без доказанной необходимости:

- микросервисы;
- универсальные платформы импорта;
- замену JPA;
- массовое переименование;
- Lombok или records только ради сокращения кода;
- нормализацию телефонов;
- новые таблицы и абстракции «на будущее»;
- обновление библиотек только ради актуальности версии.

Рефакторинг оправдан, если он устраняет:

- потерю или искажение данных;
- частичную публикацию;
- невозможность повторной обработки;
- гонки и параллельное выполнение;
- утечку секретов;
- невозможность сборки, тестирования или безопасного развёртывания;
- подтверждённую проблему производительности.

### Работа с SQL Server

- Считай production недоступным для экспериментов.
- Не выполняй `DROP`, `TRUNCATE`, массовый `DELETE` или загрузку без явного разрешения.
- Сначала используй read-only проверки.
- DDL, процедуры, seed-данные и Jobs храни отдельными профессионально названными файлами.
- Скрипты должны явно указывать порядок выполнения.
- SQL Agent Job для новой функциональности сначала создаётся отключённым.
- Первоначальная загрузка выполняется вручную на тестовой базе.
- Для больших загрузок оценивай `tempdb`, transaction log, блокировки и время.
- Не предполагай тип или размер поля, если его можно проверить в источнике.
- Не нормализуй данные без отдельного требования.

### Транзакции и интеграции

- Не удерживай транзакцию БД во время сетевого HTTP-вызова.
- Помечай документ обработанным только после успешной проверки и сохранения полного ответа.
- Замена набора дочерних строк должна быть атомарной.
- Ошибка должна оставлять данные в состоянии, пригодном для повторной обработки.
- Проверяй идентификатор сессии и полноту ответа внешнего сервиса.
- У сетевых вызовов должны быть тайм-ауты.
- Не допускай перекрывающиеся запуски одного процесса.

### Секреты

- Не печатай секреты в отчётах, diff и логах.
- Не добавляй реальные пароли или токены в Git.
- Если секрет уже опубликован, удаление из текущего файла не считается ротацией.
- Не меняй и не отзывай реальные учётные данные без отдельного разрешения.

### Тесты

Для каждого исправления сначала определи проверяемый контракт.

Минимально проверяй:

- успешный сценарий;
- пустой ввод;
- ошибку внешнего сервиса;
- повторный запуск;
- откат при ошибке;
- отсутствие частично сохранённых данных;
- поведение при параллельном запуске, если применимо.

Не отключай тесты, чтобы получить зелёную сборку.
